2026-11-20，北京时间。本稿汇总产品、架构、开源复用、安装与验证。底座处于评审阶段。四端可安装、免费开源、免产品账号和本地处理是用户要求；统一前端框架、Apache-2.0、iOS 16 及其他最低系统版本是此前的设计建议，可参加取舍。

## 一、用户应当得到什么

首装后，断网即可把一封中文 EML 导入本地档案，读信、看附件、写草稿，重启后仍可按“报销”或附件名找到原信。需要收发时再添加个人或工作邮箱，直接向服务商授权。电脑适合多栏浏览、批量处理和键盘操作；手机适合通知、回复、系统分享和离线查找。两端对发件身份、是否已提交和附件能否离线打开给出相同答案。

第一阶段交付物是 Android、iOS、macOS、Windows 客户端，附可构建的开放源码、各端安装方式和按版本列出的能力说明。所有自主实现的会员功能免费。文件保存在设备上；选用自管服务器分享大文件时，由用户指定目的地、期限并显式上传。普通邮件的附件额度、服务器配额与误删恢复仍由邮箱商决定。收到标准回执只记录相应事件，对方是否阅读不能由客户端保证。[15 项需求](01-产品需求与验收.md) · [网易权益与服务边界](02-竞品与会员功能对照.md) · [标准回执](https://www.rfc-editor.org/rfc/rfc8098.html)

### 四项改变选型的实验

1. **中文短词。** 同一批四封信中有两封包含“报销”。按三种源码策略分别复现，Meron 的短词扫描返回两封，Allodia 的默认词前缀匹配返回一封，Velo 的默认 trigram 全文匹配返回零封。这个对照只检验匹配语义。另用 Velo 原检索函数及数据库迁移测了 201 封合成信，确实出现“报销”查不到、“报销单”能查到。Meron 的扫描对大邮箱的耗时仍待测。
2. **从附件返回原信。** Velo 的第 201 个附件在数据库中存在，默认界面只过滤最近 200 个；把查询范围扩大后可以命中，但点击动作指向会话。产品需要按账号和文件名查整个已索引范围，并携带精确的邮件 ID。
3. **SMTP 确认丢失。** 在本机 GreenMail 上发送中文邮件与 CSV，收件人和密送人分别收到一封，密送头未泄露，附件内容一致。另一封信在服务端接受后模拟业务层没收到最终确认，IMAP 已能读到一封；使用同一 Message-ID 重提，变为两封。Velo 原调度器在另一个桩实验中进行了两次模拟提交。Allodia 有针对同类故障的上游用例，本轮没有把它的四端成品接入该实验。
4. **“备份”和“开源”都要验证交付边界。** Meron 的 Go 导出函数在 8 个上游样例和 1 个中文样例中通过，可保留 EML 原字节；仅此不能证明换机能恢复完整邮箱。Allodia 原始 Cargo 工作区的元数据检查成功并列出 21 个包，排除受限目录后同一命令返回 101。开源派生需整理工作区成员、可选依赖、发布包文件清单，并重新验证构建。该问题不涉及独立 MPL 引擎。[Meron 导出](https://github.com/nonbili/meron/blob/v0.5.5/desktop/eml_export.go#L228-L247) · [Allodia 工作区](https://github.com/allodia-eu/mail-calendar/blob/ff174c92c4d293c8b8280ede9b685386a401a264/Cargo.toml#L3-L8) · [可选依赖](https://github.com/allodia-eu/mail-calendar/blob/ff174c92c4d293c8b8280ede9b685386a401a264/crates/mailcal-bindings/Cargo.toml#L20-L32)

## 六、投入、退出条件与决策顺序

| 路线 | 主要投入及后续影响 | 什么证据会改变判断 | 回退办法 |
| --- | --- | --- | --- |
| A · Meron 整机派生 | 首版已有四端宿主和中文资源。投入集中在持久导入、可靠出箱、迁移与会员工具。后续同一新增界面要覆盖桌面和 KMP 手机两套交互，上游升级要持续合并差异。 | 若用同一个归档与发送执行者可以补齐核心缺口，并在两种移动系统上通过后台恢复，整机复用收益成立。如果必须同时替换存储、发件系统和手机主流程，重评成本。 | 将新增功能限制在独立模块，以标准 EML、加密清单和测试邮件迁出。验证阶段只用合成档案，切换路线无需迁移用户。 |
| B · Allodia 开源整机派生 | 四端原生和会议能力可立即研究。工作集中在简中、中文搜索、旧系统适配、资料迁移和新增会员界面。不同原生宿主及独立发布清单增加维护成本。 | 干净源码可构建、目标系统范围合适，且实际新增一项会员能力所需的多端改动小于自建宿主时，优先级上升。 | 单独采用 MPL 引擎，保留协议/日历用例。GPL 产品层签名等代码不能因改换路线就按原创 Apache 处理。 |
| C · Allodia 引擎 + 自有 React/Tauri 宿主，按需复用 Velo | 要新建四端生命周期、编辑器、IPC、系统凭据与安装工程；以后模板、规则和附件中心可共享更多 React 代码。引擎更新需重新验证其 API 与本地存储。 | 自有宿主在 iPhone 和 Android 上能正确处理中文输入、退出恢复、无界面任务，并可安全保存附件和执行队列，才给四端共用界面带来的长期收益计账。 | 单端宿主可换成原生实现，沿用引擎契约；Velo 组件如耦合前端 SQL，按行为重实现。仅在大范围互通成本得到证实时才更换协议内核。 |

**决定底座前的共同验证**用同一数据包、同一故障和同一组设备进行。先看 A、B 的现成功能和 C 的最小宿主。第一轮在一台 Mac 和一台 iPhone 对照同一条核心流程，尽早暴露签名、空账号启动和手机挂起的问题。仍满足条件的路线再扩到 Android 和 Windows；每条路线只实现验证所需的差异。按公开源码与自身品牌配置复建，记录真实投入人日、改动模块、修改过的上游文件、依赖的账户/证书和平台差异。两条整机各统计保留、局部修改、替换的模块；自有宿主路线另计每个平台的系统集成和安装工作。一个适配器或组件只有实际接入、通过相同用例，才计入节省的工作量。

1. **工作区与迁移。** 四端无产品账号导入中文 EML，冷启动能按双字词和附件名找回，原件/附件摘要一致；先在两种系统间恢复，再测错误口令、坏包、重复导入、旧任务不会重发。
2. **投递与安全。** 连接隔离测试邮箱，验证 IMAP 与 SMTP 正常路径、超时、确认不明、进程终止、重新授权、已发送副本失败；比对收件方封数。空白首启、远图邮件和本机 AI 的出站记录逐端取样，核对默认无第三方内容传输。
3. **跨端成本。** 做同一项“按附件定位原信”和一项带写入的“分类规则预览”，记录四端分别要改哪里。用备选方案的相同结果比较工时。另在目标手机与桌面用 10 万封合成信测热索引搜索 P95、索引体积、建库时间和内存。
4. **选择与交付。** 先排除未能满足免费开源分发、可靠投递和本地数据边界的实现，再对照四端实装、中文正确性、此前需求与预计长期维护量。若多条路线仍合格，以实测改造量较小且更接近现有技术经验的一条为建议。在此之前不定正式底座。

底座确定后，先交付四端可安装的本地工作区与受控收发，再交付日常工作流和可本地实现的会员能力，最后验证跨设备、端侧模型、大附件条件与发布升级。最终以 15 项需求、28 个对标分组和四端差异清单验收；仅跑通收发时发布为工程样例，完整对标有缺口时如实标明。
