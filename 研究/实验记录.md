# 开源邮箱本机实验记录

2026-11-20，北京时间。在 macOS arm64 上使用合成邮件。这里记录实际执行的步骤、输入和观察值。对日常使用的影响与改造方案见[完整方案与选型评审](../docs/06-完整方案与选型评审.md)。

## 一、中文邮件能否按平时用的词搜到

给同一批主题与正文编号，按任一字段含有查询词计算预期邮件数。所有邮件均为中文纯文本。

| 邮件 | 主题 | 正文 |
| --- | --- | --- |
| 1 | 会议邀请附件清单 | 本月会议安排与周报 |
| 2 | 十一月出差报销申请 | 请核对差旅明细 |
| 3 | 报销金额通知 | 报销凭证见附件 |
| 4 | 季度会议通知 | 讨论下周计划 |

| 搜索词 | 预期 | Meron 策略 | Allodia 策略 | Velo 策略 |
| --- | ---: | ---: | ---: | ---: |
| 报销 | 2 | 2 | 1 | 0 |
| 会议 | 2 | 2 | 1 | 0 |
| 附件 | 2 | 2 | 0 | 0 |
| 附 | 2 | 2 | 0 | 0 |
| 季度 | 1 | 1 | 1 | 0 |
| 不存在 | 0 | 0 | 0 | 0 |
| 报销申请 | 1 | 1 | 0 | 1 |

同一脚本在 Python 3.13.11／SQLite 3.51.2 和 Python 3.11.2／SQLite 3.39.4 上得到相同的命中结果。Meron 对不足三个字符的词在 Rust 中检查字段是否含该词，较长词走 trigram 索引。脚本在这组中文样本上以 SQLite 的子串匹配代替 Rust 扫描。Allodia 用词元前缀匹配，未分隔的连续汉字可能属于同一词元。Velo 默认用 trigram 匹配，一至两个字没有完整的三字片段。另以 Allodia 固定版原始建表定义在 SQLite 3.39.4 独立复核，前六个词的结果一致。这里未测带账号/日期条件的性能、拼音、繁简互搜或整机界面。[Meron 查询](https://github.com/nonbili/meron/blob/v0.5.5/meron-core/src/store/search.rs#L96-L134) · [Allodia 建表](https://github.com/allodia-eu/email-calendar-sync-engine/blob/a3cfc21e4d84920980b80f15d73cd04e956a4c1e/crates/store-sqlite/src/schema.rs#L96-L120) · [Allodia 查询](https://github.com/allodia-eu/email-calendar-sync-engine/blob/a3cfc21e4d84920980b80f15d73cd04e956a4c1e/crates/store-sqlite/src/search_ops/mod.rs#L329-L352) · [Velo 查询](https://github.com/avihaymenahem/velo/blob/4b3efd568a97b8593cff7770908c15dc82045d44/src/services/db/search.ts)

**复跑。** 在本项目目录执行以下命令。Python 的 SQLite 需支持 FTS5 和 trigram。输出包括每个策略命中的邮件编号，可检查错在哪里。[中文检索对照脚本](中文检索对照.py)

```sh
python3 -B 研究/中文检索对照.py
```

## 二、Velo 的搜索、附件与定时发送

取 Velo v0.4.21 对应提交 `4b3efd568a97b8593cff7770908c15dc82045d44`。脚本核对七个源码文件的 SHA-256，执行原数据库迁移、搜索、附件查询及定时发送逻辑。数据库使用内存 SQLite，发信服务与后台时钟由测试替身提供。环境为 Node 24.15.0、SQLite 3.51.3。[固定版源码](https://github.com/avihaymenahem/velo/tree/4b3efd568a97b8593cff7770908c15dc82045d44) · [复验脚本](Velo固定版本对照.mjs)

| 操作 | 实际观察 | 可据此设计的验收用例 |
| --- | --- | --- |
| 201 封信中仅一封含「差旅报销单审批」 | 默认查「报销」得到 0，查「报销单」得到 1，显式查 `subject:报销` 得到 1。 | 用户直接输入主题中的双字词也能找回。 |
| 201 个附件，目标文件来自最早一封邮件 | 默认接口返回 200 条，过滤目标名命中 0。扩大查询范围后命中 1，原信 ID 为 `m0`，会话 ID 为 `t0`。另核读界面源码，点击动作使用会话。 | 按所有已索引文件名检索；命中同名附件时，每个结果返回其准确原信。 |
| 将测试账号标为普通 IMAP，第一轮模拟服务接受后确认丢失，再触发第二轮调度 | 状态依次为 `pending → pending → sent`，请求 Gmail 客户端两次，模拟提交两次。没有向真实邮箱发送。 | 根据实际服务商选择执行器；结果不明的发件在重启、定时轮询时均保留待确认。 |

将该版本解压到本机，以源码目录作为参数运行，无需安装项目的 npm 依赖。[发布包](https://github.com/avihaymenahem/velo/releases/tag/velo-v0.4.21) · [附件视图](https://github.com/avihaymenahem/velo/blob/4b3efd568a97b8593cff7770908c15dc82045d44/src/components/attachments/AttachmentLibrary.tsx#L177-L183) · [定时执行器](https://github.com/avihaymenahem/velo/blob/4b3efd568a97b8593cff7770908c15dc82045d44/src/services/snooze/scheduledSendManager.ts)

## 三、确认丢失时，收件箱里到底有几封

使用 GreenMail 2.1.15、Java 21 和 Python 标准库。独立临时服务只在回环地址监听 SMTP 和 IMAP，两个收件人均为虚构的 `example.test` 用户。没有调用候选客户端代码。本实验回答的是普通 SMTP 在特定故障点的可观察后果。[GreenMail](https://greenmail-mail-test.github.io/greenmail/) · [实验脚本](本机收发对照.py)

1. 从 SMTP 发送中文主题、正文和附件「差旅报销单.csv」，含一名普通收件人及一名密送收件人。由 IMAP 分别取原件，两边各收到 1 封，均未保留密送头，中文主题、附件名与附件字节均一致。
2. 第二封信使用固定 Message-ID。服务端已返回最终的 250，在客户端协议层将这个确认截住，对业务调用方抛出断开错误。此时收件箱已有 1 封。随后故意重提完全相同的原件，收件箱变为 2 封。故障注入发生在程序内部，没有模拟真实无线断网。
3. 以收件方真实封数作为发件队列验收依据。收到最终响应前连接中断时，产品须能持久保留「发送结果待确认」。单凭 Message-ID 相同，不能假设服务商会消除重复投递。

CSV 实测 SHA-256 为 `da79dd58467209fc009076ca58efe9568287d2606e862ea8b88748bc1a9f850f`。脚本同时核对 GreenMail JAR 的 SHA-256 为 `91d58798698cac357f015365240383b936ced2f2a1a9f7db37d9e3e1a31391b1`。下载构件后，运行时可断网。[官方发布构件](https://repo.maven.apache.org/maven2/com/icegreen/greenmail-standalone/2.1.15/greenmail-standalone-2.1.15.jar)

```sh
python3 -B 研究/本机收发对照.py /path/to/greenmail-standalone-2.1.15.jar --java /path/to/java
```
